# 踩坑记录

> 分三部分：**一、二**是当前 egui/eframe 版本需要注意的坑（理解与维护代码前先读），
> **三**是旧版手写 Win32 架构踩过的深坑（换 UI 框架的决策依据，供回顾）。
>
> 配套阅读：[技术文档](技术文档.md)、[slider-feature-verification.md](slider-feature-verification.md)（PowerShell 编码坑的完整排查实录）

## 一、egui / eframe（当前版本 0.36）

### 1. `App` trait 拆分为 `logic` / `ui`

- **现象**：按旧文档实现 `fn update(&mut self, ctx, frame)` 编译报「update 不是 trait 成员」。
- **原因**：eframe 0.36 把 `update` 拆成 `logic`（每次 ui 调用前调用，且**窗口隐藏时也会被 `request_repaint` 唤醒调用**）与 `ui`（仅需要重绘时调用）。
- **对策/利用**：本项目空闲轮询托盘事件正依赖 `logic` 在隐藏时被唤醒（菜单窗口空闲时缩成 1×1 藏屏外，`logic` 仍以 100ms 周期运行）。

### 2. `clear_color` 是 trait 方法

- **现象**：`NativeOptions { clear_color: ... }` 编译报字段不存在。
- **原因**：0.36 中改为 `App::clear_color(&self, visuals) -> [f32; 4]`，每个视口可各自决定底色。
- **对策**：菜单窗口实现 `clear_color` 返回全透明，实现「菜单区域外无底色」。

### 3. `embed_viewports` 默认为 true

- **现象**：调用 `show_viewport_immediate` 后没有出现独立窗口，子菜单被当作普通 egui Window 画在父窗口里（被裁剪不可见），且不报任何错。
- **原因**：egui 0.36 的 `Context::embed_viewports` 默认 `true`——viewport 内嵌为窗口内控件；eframe 桌面端初始化时会自动 `set_embed_viewports(false)`，但自己构建 `egui::Context` 或在非常规时机调用时需注意。
- **对策**：确认 eframe 已接管；脱离 eframe 使用时手动 `ctx.set_embed_viewports(false)`。

### 4. egui 命中测试依赖上一帧的控件矩形（滞后一帧）

- **现象**：合成输入单测里，第一帧注入悬停/点击事件但 `hovered()`/`clicked()` 恒为 false。
- **原因**：hover/click 的判定基于**上一帧**注册的控件矩形做命中测试，新控件矩形下一帧才生效。
- **对策**：测试先空跑两帧预热；后续帧注入事件后断言。

### 5. 合成输入测试需清理 `textures_delta`

- **现象**：单测结束时报 `Dropped TexturesDelta with N unapplied deltas` panic。
- **原因**：无渲染器环境下 `ctx.end_pass()` 产出的字体图集纹理增量无人应用，`Drop` 里有 debug_assert。
- **对策**：测试中 `let mut out = ctx.end_pass(); out.textures_delta.clear();`。

### 6. 连续点击帧之间要插入空帧

- **现象**：合成输入测试中第二帧的点击不产生 `clicked()`。
- **原因**：上一帧的按下/释放状态（potential_click_id、双击计时）残留到下一帧，同位置的再次按下被并入上一次交互。
- **对策**：两次点击帧之间插一个无事件的空帧。

### 7. Windows + glow 的透明子窗口有已知怪癖

- egui issue #3632：用 glow 创建透明子视口在 Windows 上表现异常。本项目子菜单窗口尺寸即内容本身、不依赖透明，正好规避；主窗口透明正常。

### 8. egui 内置字体不含 CJK

- **现象**：中文渲染为方框。
- **对策**：运行时读取 `C:\Windows\Fonts\msyh.ttc` 注册进 `FontDefinitions`（app.rs `setup_fonts`）；读取失败仅退化为方框不崩溃。

### 9. 子菜单 viewport 展开的 1 帧延迟（已知取舍）

- **现象**：悬停设备行后，子菜单窗口在下一帧才出现。
- **原因**：悬停状态由上一帧绘制结果决定，窗口创建/显示随之晚一帧。
- **结论**：肉眼基本无感，接受此取舍，不做预创建优化。

### 10. `panic = "abort"` 下崩溃表象

- release profile 设置了 `panic = "abort"`：任何 panic 直接终止进程，Windows 事件日志中的异常代码可能是 `0xc0000374`（堆损坏）这类硬错误，而非托管异常。
- **对策**：排查崩溃先查事件日志（Application 日志 Id=1000/1002）拿异常代码与故障模块；Rust panic 可用 `std::panic::set_hook` 写文件兜底。

## 二、模拟输入与自动化验证

> 这些坑只影响**测试脚本**，不影响软件本身；但排查时极易误判为应用 bug。

### 1. PowerShell 5.1 按 GBK 解码无 BOM 的 UTF-8 脚本

- **现象**：脚本中某几行代码"从未执行"，行为诡异且无报错。
- **原因**：无 BOM 的 UTF-8 被按系统 ANSI（GBK）解码，中文注释的 UTF-8 尾字节与 `\r` 恰好组成 GBK 双字节字符，**回车被吞**，下一行代码与注释合并成一行变成注释。完整实锤见 [slider-feature-verification.md](slider-feature-verification.md)。
- **对策**：PS1 脚本保存为 UTF-8 **带 BOM**，或用 `pwsh`（PowerShell 7）执行。

### 2. `Add-Type` 使用旧版 C# 编译器

- **现象**：C# 代码编译报错。
- **原因**：PowerShell 5.1 的 Add-Type 不支持 C# 6+ 语法（如 `out uint x` 内联声明）。
- **对策**：用传统写法（先声明再 `out`），或改用 `pwsh`。

### 3. DPI 感知影响一切坐标 API

- **现象**：`SetCursorPos`/`GetWindowRect`/`PostMessage` 的坐标对不上应用内部坐标，数值恰好差一个缩放系数。
- **原因**：DPI-unaware 进程的坐标 API 会被系统虚拟化缩放；被测应用（PMv2）用物理像素。
- **对策**：测试脚本先 `SetProcessDPIAware()`；`PostMessage` 跨 DPI 进程投递的客户端坐标会被系统缩放（实测坐标 ×缩放系数到达目标窗口），构造事件坐标时需反推。

### 4. `PostMessage` 模拟输入对 winit 窗口不可靠

- **现象**：向菜单窗口投递 `WM_MOUSEMOVE`/`WM_KEYDOWN`，egui 偶尔收到偶尔收不到；点击配对被破坏。
- **原因**：winit 有同坐标"虚假移动"过滤（与真实光标位置互相干扰）；窗口移动到光标下方/光标离开会触发 `PointerGone`，把投递的按下/释放配对打断；键盘消息还受焦点影响。
- **对策**：**交互逻辑验证不用模拟输入**——把绘制/交互抽成纯模型（`MenuModel`），用 egui `begin_pass` + 合成 `RawInput` 事件直接测试（见技术文档 5.3 节）；真实输入只做人工目验。

### 5. `FindWindowW` 的 `$null` 参数被 PowerShell 封送为空字符串

- **现象**：按类名找窗口永远返回 0。
- **原因**：PowerShell 把 `$null` 封送成空字符串 `""` 而非 NULL 指针，导致"类名 + 空标题"匹配失败。
- **对策**：传 `[NullString]::Value`。

### 6. PowerShell 脚本块转委托静默失败

- **现象**：`EnumWindows` 的回调一次都不执行，无任何报错。
- **对策**：把枚举逻辑整体放进 C#（`Add-Type` 的方法内部用 lambda），PS 侧只拿返回字符串。

### 7. 锁屏会话下 `PrintWindow` 抓不到 OpenGL 内容

- **现象**：`PrintWindow(PW_RENDERFULLCONTENT)` 对 egui（glow）窗口截出全黑。
- **原因**：锁屏/安全桌面切换后 DWM 合成路径变化，GL 交换链内容无法被该 API 捕获。
- **对策**：不依赖截图验证；用窗口枚举（`EnumWindows` + `GetWindowRect`）做几何断言 + 纯模型单测覆盖交互。

## 三、历史版本（手写 Win32）的教训

> 旧版用裸 Win32 手绘托盘菜单（`WM_PAINT` 自绘 + 悬停弹独立子窗口），在窗口所有权、激活、销毁级联上连环踩坑，最终促使整体迁移到 egui。以下问题在 egui 中因框架接管而不复存在。

### 1. 同线程互斥锁重入死锁（"悬停设备行卡死"）

- **现象**：菜单打开后悬停设备项，整个程序永久卡死。
- **原因**：`close()` 在 `if let Some(h) = GLOBAL.lock().unwrap().take()` 体内调用 `DestroyWindow`—— scrutinee 的临时 `MutexGuard` 活到整个 if-let 结束（锁在体内一直被持有）；`DestroyWindow` 同步派发 `WM_DESTROY`，其处理函数再次 `GLOBAL.lock()` → 同线程对非重入锁二次加锁。
- **对策/教训**：先取值、释放锁、再销毁窗口；更根本的是**单线程 GUI 里用互斥锁保护全局窗口句柄本身就是伪需求**——应使用窗口附属状态（`GWLP_USERDATA`）或无锁标记。

### 2. 窗口创建失败路径的双重释放（"悬停设备行闪退"）

- **现象**：修复死锁后，悬停设备行改为直接闪退，事件日志异常代码 `0xc0000374`（堆损坏）。
- **原因**：窗口状态经 `Box::into_raw` 传入 `CreateWindowExW`，`WM_CREATE` 里 `Box::from_raw` 接管；创建中途因失活级联销毁失败后，`CreateWindowExW` 返回 `Err`，失败分支再次 `drop(Box::from_raw(state))` → 双重释放。
- **对策/教训**：跨 FFI 的堆所有权交接要用标志（"WM_CREATE 是否已接管"）保证恰好释放一次；或干脆避免"创建中途可被销毁"的时序（见下一条）。

### 3. 主菜单失活自毁与子窗口创建的时序冲突

- **现象**：子菜单创建过程中系统派发 `WM_ACTIVATE(WA_INACTIVE)` 给主菜单，主菜单按"失焦即关闭"策略自毁，级联摧毁正在创建中的子菜单窗口，触发上一条的双重释放。
- **对策/教训**：自毁类策略必须对"自己派生窗口的生命周期事件"豁免；更普世的教训是——**不要用隐式的全局副作用（失活自毁）管理窗口生命周期**，显式的开合状态更可控。

### 4. 子窗口抢焦点导致父菜单失活

- **现象**：子菜单 `SetForegroundWindow` 抢前台后主菜单立刻失活（进而触发自毁）。
- **对策/教训**：纯交互用的小窗不需要焦点——鼠标消息本来就投递给光标下的窗口。Win32 用 `WS_EX_NOACTIVATE`，egui/eframe 对应 `ViewportBuilder::with_active(false)`。

### 5. 总结论

手写 Win32 自绘菜单的难点不在绘制，而在**窗口所有权、激活时序、销毁级联与 FFI 所有权交接**——这些正是 egui/eframe 替你管理掉的部分，也是迁移决策的核心依据。
