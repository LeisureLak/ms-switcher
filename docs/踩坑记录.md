# 踩坑记录

> 分四部分：**一、二**是 egui/eframe 时期需要注意的坑（历史架构），
> **三**是第一代手写 Win32 的深坑（为什么当前架构要有那些强制规避措施），
> **四**是现代原生 Win32 架构（当前）迁移中新踩的坑。
>
> 配套阅读：[技术文档](技术文档.md)、[slider-feature-verification.md](slider-feature-verification.md)（PowerShell 编码坑的完整排查实录）

## 一、egui / eframe（当前版本 0.36）

### 1. `App` trait 拆分为 `logic` / `ui`

- **现象**：按旧文档实现 `fn update(&mut self, ctx, frame)` 编译报「update 不是 trait 成员」。
- **原因**：eframe 0.36 把 `update` 拆成 `logic`（每次 ui 调用前调用，且**窗口隐藏时也会被 `request_repaint` 唤醒调用**）与 `ui`（仅需要重绘时调用）。
- **对策/利用**：本项目空闲轮询托盘事件正依赖 `logic` 在隐藏时被唤醒（菜单窗口空闲时缩成 1×1 藏屏外，`logic` 仍以 100ms 周期运行）。

### 2. `clear_color` 是 trait 方法

- **现象**：`NativeOptions { clear_color: ... }` 编译报字段不存在。
- **原因**：0.36 中改为 `App::clear_color(&self, visuals) -> [f32; 4]`，每个视口可各自决定底色。
- **对策**：菜单窗口实现 `clear_color` 返回全透明，实现「菜单区域外无底色」。

### 3. `embed_viewports` 默认为 true

- **现象**：调用 `show_viewport_immediate` 后没有出现独立窗口，子菜单被当作普通 egui Window 画在父窗口里（被裁剪不可见），且不报任何错。
- **原因**：egui 0.36 的 `Context::embed_viewports` 默认 `true`——viewport 内嵌为窗口内控件；eframe 桌面端初始化时会自动 `set_embed_viewports(false)`，但自己构建 `egui::Context` 或在非常规时机调用时需注意。
- **对策**：确认 eframe 已接管；脱离 eframe 使用时手动 `ctx.set_embed_viewports(false)`。

### 4. egui 命中测试依赖上一帧的控件矩形（滞后一帧）

- **现象**：合成输入单测里，第一帧注入悬停/点击事件但 `hovered()`/`clicked()` 恒为 false。
- **原因**：hover/click 的判定基于**上一帧**注册的控件矩形做命中测试，新控件矩形下一帧才生效。
- **对策**：测试先空跑两帧预热；后续帧注入事件后断言。

### 5. 合成输入测试需清理 `textures_delta`

- **现象**：单测结束时报 `Dropped TexturesDelta with N unapplied deltas` panic。
- **原因**：无渲染器环境下 `ctx.end_pass()` 产出的字体图集纹理增量无人应用，`Drop` 里有 debug_assert。
- **对策**：测试中 `let mut out = ctx.end_pass(); out.textures_delta.clear();`。

### 6. 连续点击帧之间要插入空帧

- **现象**：合成输入测试中第二帧的点击不产生 `clicked()`。
- **原因**：上一帧的按下/释放状态（potential_click_id、双击计时）残留到下一帧，同位置的再次按下被并入上一次交互。
- **对策**：两次点击帧之间插一个无事件的空帧。

### 7. Windows + glow 的透明子窗口有已知怪癖

- egui issue #3632：用 glow 创建透明子视口在 Windows 上表现异常。本项目子菜单窗口尺寸即内容本身、不依赖透明，正好规避；主窗口透明正常。

### 8. egui 内置字体不含 CJK

- **现象**：中文渲染为方框。
- **对策**：运行时读取 `C:\Windows\Fonts\msyh.ttc` 注册进 `FontDefinitions`（app.rs `setup_fonts`）；读取失败仅退化为方框不崩溃。

### 9. 子菜单 viewport 展开的 1 帧延迟（已知取舍）

- **现象**：悬停设备行后，子菜单窗口在下一帧才出现。
- **原因**：悬停状态由上一帧绘制结果决定，窗口创建/显示随之晚一帧。
- **结论**：肉眼基本无感，接受此取舍，不做预创建优化。

### 10. `panic = "abort"` 下崩溃表象

- release profile 设置了 `panic = "abort"`：任何 panic 直接终止进程，Windows 事件日志中的异常代码可能是 `0xc0000374`（堆损坏）这类硬错误，而非托管异常。
- **对策**：排查崩溃先查事件日志（Application 日志 Id=1000/1002）拿异常代码与故障模块；Rust panic 可用 `std::panic::set_hook` 写文件兜底。

## 二、模拟输入与自动化验证

> 这些坑只影响**测试脚本**，不影响软件本身；但排查时极易误判为应用 bug。

### 1. PowerShell 5.1 按 GBK 解码无 BOM 的 UTF-8 脚本

- **现象**：脚本中某几行代码"从未执行"，行为诡异且无报错。
- **原因**：无 BOM 的 UTF-8 被按系统 ANSI（GBK）解码，中文注释的 UTF-8 尾字节与 `\r` 恰好组成 GBK 双字节字符，**回车被吞**，下一行代码与注释合并成一行变成注释。完整实锤见 [slider-feature-verification.md](slider-feature-verification.md)。
- **对策**：PS1 脚本保存为 UTF-8 **带 BOM**，或用 `pwsh`（PowerShell 7）执行。

### 2. `Add-Type` 使用旧版 C# 编译器

- **现象**：C# 代码编译报错。
- **原因**：PowerShell 5.1 的 Add-Type 不支持 C# 6+ 语法（如 `out uint x` 内联声明）。
- **对策**：用传统写法（先声明再 `out`），或改用 `pwsh`。

### 3. DPI 感知影响一切坐标 API

- **现象**：`SetCursorPos`/`GetWindowRect`/`PostMessage` 的坐标对不上应用内部坐标，数值恰好差一个缩放系数。
- **原因**：DPI-unaware 进程的坐标 API 会被系统虚拟化缩放；被测应用（PMv2）用物理像素。
- **对策**：测试脚本先 `SetProcessDPIAware()`；`PostMessage` 跨 DPI 进程投递的客户端坐标会被系统缩放（实测坐标 ×缩放系数到达目标窗口），构造事件坐标时需反推。

### 4. `PostMessage` 模拟输入对 winit 窗口不可靠

- **现象**：向菜单窗口投递 `WM_MOUSEMOVE`/`WM_KEYDOWN`，egui 偶尔收到偶尔收不到；点击配对被破坏。
- **原因**：winit 有同坐标"虚假移动"过滤（与真实光标位置互相干扰）；窗口移动到光标下方/光标离开会触发 `PointerGone`，把投递的按下/释放配对打断；键盘消息还受焦点影响。
- **对策**：**交互逻辑验证不用模拟输入**——把绘制/交互抽成纯模型（`MenuModel`），用 egui `begin_pass` + 合成 `RawInput` 事件直接测试（见技术文档 5.3 节）；真实输入只做人工目验。

### 5. `FindWindowW` 的 `$null` 参数被 PowerShell 封送为空字符串

- **现象**：按类名找窗口永远返回 0。
- **原因**：PowerShell 把 `$null` 封送成空字符串 `""` 而非 NULL 指针，导致"类名 + 空标题"匹配失败。
- **对策**：传 `[NullString]::Value`。

### 6. PowerShell 脚本块转委托静默失败

- **现象**：`EnumWindows` 的回调一次都不执行，无任何报错。
- **对策**：把枚举逻辑整体放进 C#（`Add-Type` 的方法内部用 lambda），PS 侧只拿返回字符串。

### 7. 锁屏会话下 `PrintWindow` 抓不到 OpenGL 内容

- **现象**：`PrintWindow(PW_RENDERFULLCONTENT)` 对 egui（glow）窗口截出全黑。
- **原因**：锁屏/安全桌面切换后 DWM 合成路径变化，GL 交换链内容无法被该 API 捕获。
- **对策**：不依赖截图验证；用窗口枚举（`EnumWindows` + `GetWindowRect`）做几何断言 + 纯模型单测覆盖交互。

## 三、历史版本（手写 Win32）的教训

> 旧版用裸 Win32 手绘托盘菜单（`WM_PAINT` 自绘 + 悬停弹独立子窗口），在窗口所有权、激活、销毁级联上连环踩坑，最终促使整体迁移到 egui。以下问题在 egui 中因框架接管而不复存在。

### 1. 同线程互斥锁重入死锁（"悬停设备行卡死"）

- **现象**：菜单打开后悬停设备项，整个程序永久卡死。
- **原因**：`close()` 在 `if let Some(h) = GLOBAL.lock().unwrap().take()` 体内调用 `DestroyWindow`—— scrutinee 的临时 `MutexGuard` 活到整个 if-let 结束（锁在体内一直被持有）；`DestroyWindow` 同步派发 `WM_DESTROY`，其处理函数再次 `GLOBAL.lock()` → 同线程对非重入锁二次加锁。
- **对策/教训**：先取值、释放锁、再销毁窗口；更根本的是**单线程 GUI 里用互斥锁保护全局窗口句柄本身就是伪需求**——应使用窗口附属状态（`GWLP_USERDATA`）或无锁标记。

### 2. 窗口创建失败路径的双重释放（"悬停设备行闪退"）

- **现象**：修复死锁后，悬停设备行改为直接闪退，事件日志异常代码 `0xc0000374`（堆损坏）。
- **原因**：窗口状态经 `Box::into_raw` 传入 `CreateWindowExW`，`WM_CREATE` 里 `Box::from_raw` 接管；创建中途因失活级联销毁失败后，`CreateWindowExW` 返回 `Err`，失败分支再次 `drop(Box::from_raw(state))` → 双重释放。
- **对策/教训**：跨 FFI 的堆所有权交接要用标志（"WM_CREATE 是否已接管"）保证恰好释放一次；或干脆避免"创建中途可被销毁"的时序（见下一条）。

### 3. 主菜单失活自毁与子窗口创建的时序冲突

- **现象**：子菜单创建过程中系统派发 `WM_ACTIVATE(WA_INACTIVE)` 给主菜单，主菜单按"失焦即关闭"策略自毁，级联摧毁正在创建中的子菜单窗口，触发上一条的双重释放。
- **对策/教训**：自毁类策略必须对"自己派生窗口的生命周期事件"豁免；更普世的教训是——**不要用隐式的全局副作用（失活自毁）管理窗口生命周期**，显式的开合状态更可控。

### 4. 子窗口抢焦点导致父菜单失活

- **现象**：子菜单 `SetForegroundWindow` 抢前台后主菜单立刻失活（进而触发自毁）。
- **对策/教训**：纯交互用的小窗不需要焦点——鼠标消息本来就投递给光标下的窗口。Win32 用 `WS_EX_NOACTIVATE`，egui/eframe 对应 `ViewportBuilder::with_active(false)`。

### 5. 总结论

手写 Win32 自绘菜单的难点不在绘制，而在**窗口所有权、激活时序、销毁级联与 FFI 所有权交接**——这些正是 egui/eframe 替你管理掉的部分，也是迁移决策的核心依据。


## 四、现代原生 Win32 架构（2026-09 迁移）的坑

### 1. GWLP_USERDATA 两跳反查混用 → 段错误

- **现象**：菜单一弹就 0xc0000005 崩溃（事件日志 1000），无 panic 输出。
- **原因**：菜单/子菜单窗口的 `GWLP_USERDATA` 存的是**宿主 HWND**（借用无所有权的设计），
  窗口过程却把它直接当 `*mut HostState` 解引用——少了一跳「宿主 HWND → 宿主的
  GWLP_USERDATA → HostState 指针」反查。
- **对策**：两跳反查写成固定模式并加注释；两处窗口类不得混用取值方式。

### 2. `PostMessage(WM_MOUSEMOVE)` 会被系统合并掉

- **现象**：向菜单窗口投递带坐标的 `WM_MOUSEMOVE`，过程收到的却是真实硬件消息的坐标。
- **原因**：系统对队列里的 `WM_MOUSEMOVE` 有合并（只保留最新）行为，真实输入一到，
  投递的移动消息被顶掉——与踩坑记录 二-4（winit）同类，纯 Win32 也不例外。
- **对策**：自动化测试用 `SetCursorPos` / `SendInput` 注入**真实输入**；
  `PostMessage` 只用于自定义消息（`WM_APP_*`）与键盘消息（键盘消息无此合并）。

### 3. COLORREF 字节序是 0x00BBGGRR

- **现象**：悬停高亮显示成橙红色，期望的 `#0078D7` 蓝色完全不对。
- **原因**：按 RGB 直觉写了 `COLORREF(0x000078D7)`；COLORREF 实际是 B/G/R 倒序。
- **对策**：蓝色写 `0x00D77800`；灰阶（对称值）不受影响，更易漏。

### 4. 隐藏 owner 导致 `IsWindowVisible` 返回 false

- **现象**：菜单明明显示在前台（`GetForegroundWindow` 都指向它），
  `IsWindowVisible(menu)` 却是 false。
- **原因**：菜单是隐藏宿主窗口的 owned window，`IsWindowVisible` 会沿 owner 链检查。
- **对策**：判断菜单是否可见改用样式位（`GWL_STYLE & WS_VISIBLE`）、`FindWindow` 或截图。

### 5. DPI 虚拟化影响测量进程

- **现象**：DPI-unaware 的 PowerShell 里 `GetWindowRect` 量出 320×274，
  DPI-aware 进程量同一个窗口是 640×548（200% 屏）。
- **原因**：坐标系被系统按进程 DPI 感知度虚拟化（踩坑 二-3 的应用侧视角）。
- **对策**：测量/截图脚本先 `SetProcessDPIAware()`；不能据此误判应用布局错误。

### 6. windows crate 0.62 的 API 形状备忘

- `PostMessageW`/`GetMessageW`/`SetFocus` 的 HWND 参数是 `Option<HWND>`；
  `SendMessageW` 的 HWND 是裸值、wparam/lparam 是 Option。
- `NOTIFYICONDATAW` 的 `uVersion` 在 union `Anonymous` 字段里（x64 定义）。
- `TBM_GETPOS` 未导出，值为 `WM_USER`（1024）。
- `TrackMouseEvent` 要 `&mut TRACKMOUSEEVENT`；`WM_MOUSELEAVE` 在 `UI::Controls` 模块
  （crate 按头文件来源归档，不在 WindowsAndMessaging）。
- Rust 2024：`static mut` 引用被禁（改用 `AtomicU32`/`OnceLock`），
  `unsafe fn` 体内需要显式 unsafe 块（本 crate 统一 `#![allow(unsafe_op_in_unsafe_fn)]`）。
- edition 2024 + `panic = "abort"`：panic 直接终止且 GUI 子系统无 stderr，
  排查崩溃先查事件日志（Application Id=1000）拿异常代码与偏移。

### 7. 托盘 HICON 的 RGBA → DIB 转换

- `CreateDIBSection` 用**负高度** `BITMAPINFOHEADER`（top-down）+ 32bpp，
  `CreateIconIndirect` 后立即释放临时 HBITMAP（系统会复制）；
  掩码位图用 `CreateBitmap(w, h, 1, 1, None)` 单色即可。

### 8. GDI 字体高度是物理像素，必须按 DPI 缩放

- **现象**：200% 屏上菜单文字只有期望大小的一半（用户反馈「字体特别小」）。
- **原因**：`CreateFontW(-13)` 的高度是物理像素，不随 DPI 自动缩放；布局坐标
  全都乘了 DPI，唯独字体没乘。
- **对策**：字体按 `-(13 * GetDpiForWindow / 96)` 创建，且随菜单开/关创建/销毁
  （不能做全局单例——多显示器不同 DPI 时会取错）。

### 9. 子菜单屏幕边缘避让

- **现象**：主菜单贴屏幕右缘时子菜单仍向右展开，大片被截断（用户反馈）。
- **对策**：双保险——① 主菜单打开时就按「菜单+子菜单」全宽对工作区夹取；
  ② 子菜单展开前用 `MonitorFromWindow(主菜单)` 查工作区，右缘放不下且左侧
  足够时改为贴主菜单**左缘**展开，垂直方向同时夹取到工作区内。

### 10. 子菜单关闭的时序纪律

- 指针从子菜单移回主菜单设备行时：`WM_MOUSELEAVE`（子菜单）先处理，
  此时主菜单的 `WM_MOUSEMOVE`（硬件消息）尚在队列中。若同步关子菜单会误关。
- **对策**：关闭一律 `PostMessage(WM_APP_CLOSE_SUBMENU)`，处理时重新检查
  `model.sub_hover`（硬件消息先于投递消息被处理，此时状态已更新）——
  正是迁移计划 §10.3 的「失活只投递 + 处理时重查」。

### 11. `Shell_NotifyIconW` 漏了 `NIF_ICON` → 托盘图标空白

- **现象**：托盘显示空白占位图标（用户反馈「托盘没有图标」）。
- **原因**：`NOTIFYICONDATAW` 里明明填了 `hIcon`（纯代码生成的 HICON），
  但 `uFlags` 只写了 `NIF_MESSAGE | NIF_TIP`——不带 `NIF_ICON` Shell 根本
  不会读 `hIcon` 字段。不报错、不返回失败，纯粹静默忽略。
- **对策**：`uFlags: NIF_MESSAGE | NIF_ICON | NIF_TIP`。另外掩码位图
  `CreateBitmap` 不初始化位数据，务必传清零的缓冲（见 四-7 的修正）；
  图标按 `GetSystemMetrics(SM_CXSMICON)` 生成（进程 PMv2 下随 DPI 缩放）。
- exe 图标是另一回事：需要在 build.rs 里用 `winresource` 把 `assets/icon.ico`
  作为资源编译进 exe（`tools/gen_icon.py` 生成多尺寸 ICO）。

### 12. 托盘弹窗 `SetForegroundWindow` 被前台锁静默拒绝 → 点外面不关菜单

- **现象**：菜单打开后点击菜单外空白处不关闭，必须再点一次托盘图标或 Esc。
- **原因**：失焦关闭依赖 `WM_ACTIVATE(WA_INACTIVE)`；但从托盘点击打开弹窗时，
  Windows 前台锁（foreground lock timeout）常让 `SetForegroundWindow`
  **静默失败**——菜单看起来在前台实际从未激活（`WA_ACTIVE` 都没收到过），
  之后再点哪儿都不会产生失活事件。
- **对策**：标准的 AttachThreadInput 技巧——临时把当前线程附加到前台窗口
  所在线程的输入队列，再 `SetForegroundWindow` + `SetFocus`，然后解除附加
  （`windows 0.62` 中该函数在 `Win32::System::Threading`，不在
  `WindowsAndMessaging`）。判定「从未激活」的 `menu_ever_active` 豁免逻辑保留。

### 13. 子菜单含子控件后，悬停滑块就关闭子菜单

- **现象**：子菜单加入 Trackbar 滑块后，指针一移到滑块上子菜单就消失。
- **原因**：滑块是子窗口控件，指针从子菜单窗体移到子控件上时，父窗口
  收不到 `WM_MOUSEMOVE` 只会收到一次 `WM_MOUSELEAVE`——被当成「离开
  子菜单」走了关闭路径。此前子菜单全是自绘内容，命中不到这个坑。
- **对策**：子菜单 `WM_MOUSELEAVE` 先 `GetCursorPos` + `GetWindowRect`
  判断光标是否仍在窗口矩形内：在内（= 移到滑块上）就保持打开，且**不要
  重挂 TrackMouseEvent**（重挂会在子控件上来回触发 leave）；「从滑块直接
  拖出窗口」的路径由滑块子类（子类 id 3）自己登记 leave 并向宿主投递
  `WM_APP_SUB_LEFT`，宿主处理时重新检查光标位置与悬停状态。
  注意：`windows` crate 的 `WM_LBUTTONDOWN` 若未导入，match 里写裸标识符
  会变成**绑定模式**静默吞掉所有消息并让后续分支 unreachable——编译器
  只给 warning，务必看。

### 14. 失焦关闭的最终兜底：菜单打开期间装 WH_MOUSE_LL 钩子

- **背景**：四-12 的 AttachThreadInput 修复在实测中仍不够——部分时序下
  `SetForegroundWindow` 失败或失活事件丢失，点空白处依旧不关菜单。
- **对策**：不依赖激活状态，菜单打开期间安装低级鼠标钩子
  （`WH_MOUSE_LL`，全局，仅菜单存活期存在）：`WM_LBUTTONDOWN`/
  `WM_RBUTTONDOWN` 时 `WindowFromPoint` → `GetAncestor(GA_ROOT)` →
  按窗口类名（`MSS_Menu`/`MSS_SubMenu`）判断是否落在自己的弹出层内，
  之外则 `PostMessage(WM_APP_CLOSE_MENU)`。事件照常 `CallNextHookEx`
  放行，不影响其它程序；钩子回调与消息循环同线程，可直接读静态量。
- **坑**：托盘图标点击落在菜单外，钩子会在**按下时**投递关闭——随后
  抬起时 `WM_APP_TRAY` 的 toggle 看到菜单已关会**重新打开**。实际时序
  中关close先于 tray up 被处理（closed 队列在前），toggle 判 menu=None
  后不再开，行为正确；但若改动消息顺序需重新验证这条路径。

### 15. 按钮按下反馈：LBUTTONUP 直接触发 → 改为「按下登记、松手核销」

- 之前所有可点区域都在 `WM_LBUTTONUP` 立即执行动作，没有任何按动反馈。
- **对策**：`WM_LBUTTONDOWN` 在命令区登记按压态（`pressed`/`sub_pressed`，
  悬停色深一档的按压色绘制），`WM_LBUTTONUP` 时重新命中测试，与按压态
  一致才触发动作；`WM_MOUSELEAVE` 清除按压态（按住拖出视同取消）。

### 16. LL 钩子回调内 `SendInput` → win32k 自锁，进程卡死且杀不掉（"开滚轮模式就死"）

- **现象**：开启滚轮模式后按住触发键动两下，整个进程永久卡死；任务管理器
  「结束任务」、`taskkill /F` 全部报「没有此实例」——进程变成**杀不掉的
  僵尸**：只剩一个线程停在不可中断的内核等待里（`Waiting/Executive`，
  CPU 时间冻结），进程对象不回收，单实例互斥体也不放，新实例起不来，
  只能重启系统。
- **原因**：滚轮注入原来直接在 `WH_MOUSE_LL` 回调里 `SendInput`。注入的
  输入要走**同一条低级钩子分发路径**，回调内注入等于让线程在 win32k 的
  输入处理临界区里自己等自己——确定性死锁，100% 复现。这类内核态自锁
  不响应 `TerminateProcess`（终止 APC 要线程回到可中断点才执行）。
- **对策**：**LL 钩子回调内只允许内存运算和 `PostMessage`**。注入改为：
  回调里 `PENDING_WHEEL.fetch_add` + `INJECT_POSTED` 合并标志投递
  `WM_APP_SCROLL_INJECT`，宿主在普通消息处理上下文 `flush_pending_wheel`
  里统一 `SendInput`（先清标志再取量，防丢量）。同类隐患一并排除：
  关闭菜单钩子里的 `WindowFromPoint`（会向命中窗口的宿主线程同步发
  `WM_NCHITTEST`，对方挂起同样拖死本线程）改为只 `GetWindowRect`
  本线程自有菜单/子菜单窗口矩形做包含判断。
- **教训**：钩子回调是「内核输入分发上下文」，不是普通消息处理上下文；
  凡会再进入输入分发/跨线程同步消息的 API（`SendInput`、`WindowFromPoint`、
  `SendMessage` 外国窗口等）一律禁止，需要副作用就投递回消息循环再做。
- **排查工具**：线程状态/等待原因用 `Win32_Thread`（WMI）；等待链用 WCT
  （`OpenThreadWaitChainSession`/`GetThreadWaitChain`，advapi32）——
  本例链上只有自己一个节点，说明不是被别的线程拖住而是内核内部自锁。

### 17. LL 钩子吞掉移动后 `pt` 不再可靠 → 差分出反向位移 → 滚动回弹

- **现象**：滚轮模式按住触发键移动轨迹球，页面确实滚了一段距离，但过一下
  就整体回弹（向反方向滚回去）。
- **原因**：位移最初用钩子事件 `MSLLHOOKSTRUCT.pt` 差分求得。`pt` 是
  **光标位置**而非原始位移；把所有 `WM_MOUSEMOVE` 吞掉冻结光标后，系统
  的输入位置与真实光标位置脱节，会生成把位置**拉回真实光标**的补偿移动
  事件（非注入标记，与普通移动无异）。补偿事件在回调里表现为反向的大段
  位移 → `dy` 反号 → 注入反向滚轮 → 页面回弹。此外 `pt` 还带指针弹道
  （加速度）并在屏幕边缘被钳制，同样污染差分。
- **对策**：位移源换成 **Raw Input**——`RegisterRawInputDevices` 以
  `RIDEV_INPUTSINK` 把宿主窗口注册成鼠标输入 sink，后台也收 `WM_INPUT`，
  读 `RAWMOUSE.lLastY` 相对位移攒齿。Raw Input 由 HID 栈直接产生，LL 钩子
  吞掉 legacy 移动消息不影响它的投递；无弹道、无钳制、无补偿事件。
  LL 钩子只保留三件事：识别触发键按下/抬起、吞移动冻结指针、触发键录入。
  注意 `MOUSE_MOVE_ABSOLUTE` 设备（手写板等）的 `lLastY` 是绝对位置要跳过。
- **教训**：想在「光标不能动」的前提下拿位移，就别碰光标坐标——`pt` /
  `GetCursorPos` / `WM_MOUSEMOVE` lParam 全是光标坐标系；原始位移只有
  Raw Input 给。这也是微软对 LL 钩子的官方建议：监控输入用 Raw Input，
  钩子只用来做放行/吞掉的门卫。
- **顺带修复**：菜单打开瞬间触发键恰好按着时，其抬起事件会被「菜单打开
  整体放行」路径吃掉，`scroll.active` 永久卡 true 吞掉所有移动——
  `open_menu` 里顺带复位；`set_enabled(false)` 同样复位。

### 18. 菜单关闭后前台焦点锁死在任务栏（"焦点还给了通知区域"）

- **现象**：点托盘图标开菜单、用完后关闭，键盘焦点停在任务栏上——
  用户要回到自己原来的窗口必须再点一下（实测：关闭前 fg=Chrome，
  关闭后 fg=Shell_TrayWnd）。
- **原因**：菜单是前台窗口，被销毁时系统把激活让给通知区域；加之
  `close_menu` 末尾还主动调 `NIM_SETFOCUS`（该 API 的作用就是「把焦点
  还给通知区域」，本来是为键盘打开托盘菜单的场景设计的），焦点彻底
  留在托盘图标上。
- **对策**：菜单销毁前主动把前台归还给用户窗口（`win32/focus.rs`）：
  当前前台已是正常用户窗口（点击菜单外关闭时系统已激活点击目标）则
  不动；否则按 Z 序取最上层符合 **Alt+Tab 口径**的窗口（可见、非本
  进程、无 `WS_EX_NOACTIVATE`、未 `DWMWA_CLOAKED`、无 owner 且非
  TOOLWINDOW——除非显式 `WS_EX_APPWINDOW`），附加输入线程后
  `SetForegroundWindow` 移交；找不到目标才退回 `NIM_SETFOCUS`。
- **次坑 1：Win11 任务栏部件是「可见、可激活」的顶层窗口**。任务栏
  「开始」按钮实为 owner=Shell_TrayWnd 的 `Button` 类顶层窗口
  （TOOLWINDOW|TOPMOST|LAYERED，无 NOACTIVATE），Z 序还在普通窗口
  之上——只靠「可见+非 Shell 类名」过滤会把它选中。按 Alt+Tab 口径
  （owner/TOOLWINDOW 过滤）才能排除，Shell 类名黑名单仅作兜底。
- **次坑 2：持有前台 ≠ 有权移交前台**。实测本进程窗口已是前台时，
  裸调 `SetForegroundWindow(目标)` 仍返回失败——前台锁看的是「线程
  输入状态」而非「进程持前台」，从没收到真实输入的线程不算数。
  正确姿势是把**本线程附加到目标线程**的输入队列
  （`AttachThreadInput(cur→target, true)`）再调用，附加方向与
  打开菜单时的 `force_foreground`（fg→cur）相反。
- **验证手段**：`PostMessage(MSS_Host, WM_APP_TRAY, 1, WM_LBUTTONUP)`
  可模拟托盘点击开菜单、`WM_APP_CLOSE_MENU` 模拟关闭，配合
  `GetForegroundWindow`+`GetClassNameW` 观察前台流转；
  `MSS_DEBUG_FOCUS=1` 让 `focus::restore` 把判定过程写
  `%TEMP%\mss_focus.log`（GUI 子系统没有 stderr）。

### 19. 录入结果改了模型却没标脏子菜单 → 界面「按了没反应」

- **现象**：设备子菜单点「触发键」录入，按下目标按键后子菜单仍显示
  「按下任意鼠标键…」，必须再点一下别处或关掉菜单才能看到新触发键。
- **原因**：`WM_APP_SCROLL_CHANGED` 的处理更新了 `model.sub_scroll`
  与 `model.capturing`，但收尾的 `invalidate_menu` 只
  `InvalidateRect(主菜单)`——触发键行与录入提示都画在**子菜单**上，
  子菜单从不被标脏，要等无关事件（悬停变化、子菜单内 `WM_LBUTTONUP`、
  重开菜单）碰到重绘才显示新值。模型早已更新，纯是重绘缺失。
- **对策**：宿主的重绘帮助函数改为同时标脏 `state.menu` 与 `state.sub`
  （`invalidate_menus`）。教训：双窗口自绘 UI 里「刷新界面」必须覆盖
  所有画出该状态的窗口，不能默认只有一个。
- **次生坑 1（钩子次序不定）**：录入靠「菜单外一次按键」结束，这次点击
  还会到达菜单关闭钩子。两个 LL 钩子调用次序不定——滚轮钩子先跑时
  `CAPTURING` 已被清，关闭钩子便把该点击误判为「点菜单外」投递
  `WM_APP_CLOSE_MENU`：菜单一关，刚录入到 `sub_scroll` 预览里的
  触发键随之丢失。对策：滚轮钩子吞掉结束录入的事件时把
  `MSLLHOOKSTRUCT.time` 记入 `CAPTURE_END_TIME`，关闭钩子对同
  时间戳的事件豁免——与次序无关（`is_capture_end_event`）。
- **次生坑 2（静默取消）**：原设计「菜单内任意按下 = 取消录入」，但用户
  最自然的手势是点完录入原地按侧键，会被静默取消且（因上面的重绘缺失）
  界面毫无反馈。现改为菜单内仅**左/右键**取消，中键/侧键不与菜单交互、
  原地按下照常录入。

### 20. 键盘触发滚轮模式：组合键触发时立即取消且键盘事件不灭活

- **现象**：用户想用 `Alt` 作滚轮模式开关键，但又怕 `Alt+Tab`/`Alt+F4`
  等组合快捷键失效。
- **需求**：单键触发，非组合键；按住键盘开关键时进入滚轮模式，一旦又按下
  其它任意键立即取消；键盘事件不灭活（`CallNextHookEx` 正常放行）。
- **对策**：
  - `WH_KEYBOARD_LL` 钩子仅观察，不吞非录制键；注入事件（`LLKHF_INJECTED`）
    忽略。
  - 256 位键位图记录当前按下的归一化虚拟键；左/右 Shift/Ctrl/Alt/Win
    统一映射到同一侧（`0xA0/0xA1→0x10`，`0xA2/0xA3→0x11`，
    `0xA4/0xA5→0x12`，`0x5B/0x5C→0x5B`），避免左右 Alt 切换时状态混乱。
  - `kb_held = 开关键按位 && 位图中无其它键`；进入或退出滚轮模式时
    走 `ScrollEngine::sync_active` 统一状态，与鼠标触发来源互不冲突。
  - 录制键盘触发键时吞掉该次按键（含 `Esc` 取消），避免菜单/应用误处理；
    普通滚轮模式期间键盘事件全部放行。

### 21. 同一规则同时支持鼠标与键盘触发来源

- **现象**：规则同时配置了鼠标侧键与 `Alt`，侧键按住滚动时用户按了 `Alt`
  想切键盘触发；或 `Alt` 按住滚动时用户不小心按下侧键。
- **对策**：`ScrollEngine` 拆出 `mouse_held` 与 `kb_held` 两个来源标志，
  `active = enabled && (mouse_held || kb_held)`。任一来源的释放或取消只清除
  自己的标志，最终 `active` 由二者共同决定。菜单打开、规则失效、功能关闭
  时统一清零两个标志并 `sync_active`，防止钩子再见不到抬起事件而永久激活。

### 22. Win 键作滚轮模式开关键时弹 Start 菜单

- **现象**：把 `kb_trigger` 设为 Win（LWin/RWin）后，按住 Win 可以进入滚轮模式，
  但一松开 Win 就打开 Windows Start 菜单；若直接吞掉 `Win up` 虽能阻止 Start 菜单，
  但会导致系统认为 Win 键一直按住，后续按键都变成 `Win+某键`。
- **原因**：Windows 对单独 Win 键的处理是 down → 无其它键盘按键 intervening → up
  后，在 **up** 时打开 Start 菜单。键盘触发滚轮模式原本只观察不吞键，所以
  `Win up` 被系统收到，Start 菜单弹出；直接吞 `Win up` 又会让系统/应用看不到释放。
  此外，Win 键按住期间会持续产生 auto-repeat `Win down` 事件，任何太早注入的
  掩码键都会被这些重复 down 事件“刷掉”，所以仅在第一次滚动时注入掩码并不可靠。
- **经验**：要阻止 Start 菜单，掩码键必须紧贴在最后那个物理 `Win up` 之前，
  并且要把物理 `Win up` 换成一次**注入的** `Win up`，才能在“不弹 Start”和
  “不卡 Win 键”之间同时满足。
- **对策**：
  - 在 `ScrollEngine` 增加 `has_scrolled`（本次 hold 是否实际注入过滚轮）和
    `kb_interrupted`（本次 hold 是否出现过组合键）两个标志，进入滚轮模式时
    `sync_active` 重置。
  - `queue_wheel` 每次注入一齿时置 `has_scrolled = true`。
  - `keyboard_hook_proc` 在 `Win up` 时判断：当前 `kb_trigger` 是 Win、
    抬起前 Win 单独按住、本次 hold 滚过、未出现组合键。四项全满足则
    吞掉物理 `Win up`，并调用 `SendInput` 注入左 Ctrl（scan 0x1D）
    down + up + `Win up`。Windows 把本次 Win 释放识别为 `Win+Ctrl`
    组合键序列，从而不打开 Start 菜单；同时注入的 `Win up` 释放 Win 键，
    避免逻辑卡死。
  - 组合键触发（非触发键按下导致 `kb_held` 失效）时设置 `kb_interrupted`，
    不投递 dummy，保证 `Win+Tab`/`Win+R` 等不受影响。
  - 轻点 Win 没有滚动时，`has_scrolled == false`，`Win up` 正常放行，
    Start 菜单仍可打开。

### 23. GUI 子系统程序在 PowerShell 没有 stderr

- **现象**：设置了 `MSS_DEBUG=1` 从 PowerShell 启动程序，却看不到 `eprintln!`
  输出的调试日志。
- **原因**：项目为 `#![windows_subsystem = "windows"]`，启动时不附加控制台，
  因此标准错误句柄没有绑定到 PowerShell 的管道。
- **对策**：给 `HostState` 增加 `debug_log` 方法：`MSS_DEBUG=1` 时除 `eprintln!`
  外，还把日志追加到 `%TEMP%\mss_debug.log`，方便在 GUI 进程中也能看到滚动、
  键盘等关键路径的输出。

### 24. 全局配置编辑值不能继续复用当前系统值

- **现象**：主菜单顶部滑块直接读取当前系统速度时，设备配置一生效，滑块就变成设备值；用户想预先编辑全局配置，却会直接改当前速度并使设备配置失效。
- **原因**：同一组 `MenuModel::speed_val/wheel_val` 同时承担“当前系统观测值”和“持久化全局配置值”，模型没有表达配置来源。
- **对策**：顶层配置增加 `speed` / `wheel`，主菜单滑块只绑定这两个持久化值；是否写系统由 `AppState::global_active` 决定。设备配置生效时编辑全局值只落盘，不切换配置。设备列表另加固定的全局项，设备项使用 toggle：再次点击当前设备统一回到全局配置。
- **测试要点**：合成输入测试覆盖全局项/设备项点击与键盘焦点映射；状态测试覆盖“编辑全局不影响当前设备”“当前设备再次点击回全局”“恢复默认删除整个 `cfg.scroll`”。

### 25. 睡眠唤醒/安全桌面会丢按键 up 事件 → 触发键残留卡死或永远失活

- **现象**：睡眠再唤醒后，滚轮模式可能整体卡死（光标被永久冻结、所有移动被吞），
  也可能表现为触发键「无效」（按住没反应）。用户并没有在睡眠期间抬起按键。
- **原因**：`KEYS_DOWN` 位图与 `mouse_held`/`kb_held` 标志完全由钩子投递的
  down/up 事件维护，但事件投递本身不可靠：
  - **USB 挂起重置**：睡眠时设备断电重置，「按住」状态在设备侧已消失；
    唤醒后物理松开时设备根本不认为它按着 → up 事件永远不来；
  - **安全桌面**（UAC/锁屏/凭据框）：LL 钩子在安全桌面上收不到任何事件，
    期间松开的键全部丢失；
  - 残留的**触发键**位让 `kb_held` 永远为真 → 卡死；残留的**其它键**位让
    `any_key_down_except` 永远为真 → 触发键永远无法激活（「无效」）。
    打开托盘菜单只复位 held 标志不清位图，关菜单 `sync()` 里的
    `update_kb_active` 又会按残留位把它激活回来——自救无效。
- **经验**：判断「键是否还按着」不能依赖「收到过哪些事件」，要问系统
  「现在物理上是什么状态」——`GetAsyncKeyState` 读的是当前物理态，
  与事件是否送达、是否被我们吞掉都无关。事件位图只适合回答
  「这次事件的键是什么」，不适合回答「现在还按着什么」。
- **对策**：
  - `phys_down`/`canon_phys_down`（归一化修饰键查左右两个具体键码）/
    `trigger_btn_phys_down`（鼠标触发键 → VK_*BUTTON）直接查物理态；
  - `kb_only_trigger_held`：触发键是否按住改用物理态判定；「其它键」
    仍用事件位图，但先 `reconcile_keys` 把位图中物理已松开的残留位
    清掉再判组合；
  - `mouse_hook_proc` 在 `active` 期间每个事件顺手校验两个触发源的
    物理态，已松开就清标志（鼠标移动事件频率高，瞬间自愈）；
    `keyboard_hook_proc` 对称地校验鼠标触发键——无论哪种触发源丢
    up，任意一个输入事件到达即恢复；
  - 副作用（可接受且更正确）：`sync()`/`update_kb_active` 时物理正
    按着触发键会立即激活滚轮模式（与注释中「规则切到带键盘触发时
    用户正按住」的预期一致）；极快地点按（事件到达回调前已松开）不
    再触发滚轮模式——本来就该如此。
